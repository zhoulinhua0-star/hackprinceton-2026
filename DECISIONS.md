# Decisions

A log of choices and why, so nobody re-argues them at 3am. Format: `N. **Decision.** Why. (team | Claude)`. A reversed decision stays and is marked "Superseded by #N".

1. **Build Syllabus Crew** (fallback: Group Chat Murder Mystery). Strongest fit for four tracks. (team)
2. **Enter Photon iMessage, Amazon, and Education tracks; Photon Voice only if voice gets built.** One product, a different pitch opening per judge. (team)
3. **Pitch it as a personal agent for students, not a study app with AI.** "Personal agent" must be visible: acts unopened, talks, remembers, acts in real tools, asks first. (team)
4. **Tutor is the main feature; syllabus scanning is table stakes.** Without the Tutor loop it's "Ahead in iMessage." (team)
5. **Channel: iMessage via Photon 2.0 beta, replacing the PWA + web push plan.** Students already live in iMessage; no install step. (team)
6. **Two surfaces: iMessage thread (main) + web dashboard (secondary).** Judges need a laptop view; students don't. (team)
7. **Beta limits drive UX: text A/B/C quizzes, "Reply YES or NO", syllabus as a photo.** Photon Beta iMessage has text and images only. (team)
8. **Inbound-first onboarding (sms: link / QR); the agent never cold-texts.** Outbound-first triggers Apple's "Report Junk" banner and risks the line. (team)
9. **Five agents: Crew Lead (router) + Scout, Tutor, Planner, Nudger.** Scout so the agent doesn't wait for uploads; Nudger because it makes real decisions. (team)
10. **Hard rules in code, not prompts:** approval gate, quiet hours 11pm-8am, max 3 quizzes and 3 nudges per day, read-only Scout, reply matching. They hold even if the model ignores its prompt. (team)
11. **The Planner has no calendar-write tool; only `createProposal`.** The calendar is written only by the approve path (YES text or dashboard Approve). (team)
12. **Code for math, LLM for language.** Grading A/B/C, mastery, priority, crunch detection, and timing are deterministic. The LLM handles parsing, writing, Socratic prompts, and routing. (team)
13. **Scout: generic iCal must-have; Gmail is a stretch; the demo "Week 6 slides" moment is staged.** iCal is LMS-agnostic; no Canvas-specific code or LMS API (policy + time). (team)
14. **Voice is a stretch only** (Tutor phone quiz on a Photon SMS number). (team)
15. **The demo syllabus parse is pre-loaded; the dashboard "animates in."** The loop must never depend on live parsing. (team)
16. **Two demo states (Day 1, Week 6) + hidden controls + reset.** Mastery can't drop right after onboarding. (team)
17. **Stack: Bedrock (Converse + tool use, no agent framework), Textract, DynamoDB, EventBridge, Google Calendar, node-ical, Next.js on Vercel.** Amazon services for the Amazon track; ~50-line agent loop. (team) LLM part was superseded by #32, then restored by #34.
18. **Agent behavior lives in `agents/<name>.md`.** Change behavior by editing markdown, not code. (team)
19. **Demo uses a fake `.ics` hosted with the dashboard and a demo Google account.** No real courses on the projector; same code path. (team)
20. **Address competitors on a slide before judges ask.** (team)
21. **Walking skeleton first: every outside service behind an interface with a fake** (Messenger, LLM, Calendar, Store). The loop runs end to end on canned data before any real integration besides Photon. (Claude)
22. **Start with an in-memory store, swap to DynamoDB in task 7.** Unblocks the loop; Dynamo stays in the plan for the Amazon track. (Claude)
23. **Agent server is a long-running Node/TS process (assumed).** Simplest for streams, timers, and typing indicators; revisit after reading the Photon beta docs. (Claude)
24. **Build scheduling as an in-process cron first; move to EventBridge Scheduler if time allows.** Fewer moving parts during the build. Demo uses hidden controls anyway. (Claude)
25. **Dashboard live updates by polling every ~2s.** Good enough on stage; no websocket infra. (Claude)
26. **Staged parse triggers on "Day 1 demo mode + first image received", not image hash.** iMessage may re-compress the photo, so a hash match could fail on stage. (Claude)
27. **The demo quiz question is fixed seed data; follow-ups and proposals come from the LLM with canned fallbacks (~4s timeout).** Guarantees "clearly from the Week 6 slides" and survives slow Wi-Fi. (Claude)
28. **Mastery: wrong → m × 0.7, right → m + (1 − m) × 0.3; Ch. 5 starts at 50%, drops to 35%.** Visible drop; matches the earlier 35% mockup. (Claude)
29. **Priority = grade weight × (1 − mastery) × 1/max(1, days to exam).** Direct encoding of the brief's formula. (Claude)
30. (Refined by #42.) **One pending reply item per student at a time.** Makes A/B/C vs YES/NO matching unambiguous; anything unclear gets a clarifying text. (Claude)
31. **Quiet hours in America/New_York.** The event is in Princeton, NJ. (Claude)
32. **Use the Gemini API instead of Claude on Bedrock for all LLM calls.** Builder's choice. It's behind the `LLM` interface, so it's swappable. Cost: weaker Amazon-track stack story; keep Textract, DynamoDB, and EventBridge to compensate. (team) Superseded by #34.
33. **One project enters all 4 tracks (Photon iMessage, Photon Voice if built, Amazon, Education).** Confirmed with the event. (team)
34. **Back to Claude on Amazon Bedrock for all LLM calls; default model Claude Haiku 5.5.** Builder's choice. Restores the full AWS story for the Amazon track. (team)
35. (Superseded by #40.) **Haiku 5.5 for every LLM call, including syllabus parsing. Sonnet 5.5 only if a test shows Haiku falls short.** The most likely weak spot is syllabus text → JSON on the 5 real syllabi (task 8); next is quiz quality. Haiku is fast and cheap, and latency matters on stage. The model is set per use by env var, so switching to Sonnet needs no code change. (team)
36. **Call Bedrock through the Anthropic SDK's Bedrock client (`AnthropicBedrockMantle`, Messages API) instead of the raw Converse API.** Same Bedrock billing and AWS story, with native Claude tool-use types and SDK helpers. (Claude)
37. **Photon: shared iMessage line (+1 628 502 3837), project `hackprinceton`, builder's number assigned.** Enough for the demo (cap 25 users). A shared line can only reply in direct chats to someone who has an active assignment and has texted first, which matches the inbound-first rule. Each judge/user needs an assignment before the QR flow works. (team)
38. **Use `@photon-ai/api` (Beta client) over the WebSocket for inbound, HTTP `sendMessage` for outbound. Not spectrum-ts.** spectrum-ts is the Stable SDK; the beta docs say not to mix them. WebSocket needs no public URL, so no tunnel for local dev. Revisit webhooks if the agent is deployed serverlessly. (Claude)
39. **No typing indicator on the shared iMessage line; call it best-effort and never rely on it.** Real test: `space.typing.update` returns 422 `UNSUPPORTED_CONTENT`. The brief assumed typing indicators; for slow replies (LLM calls), send nothing or a short "On it" text instead. A dedicated line may support typing; untested. (Claude)
40. **Bedrock models: Haiku 4.5 as the default, Sonnet 4.6 for syllabus parsing.** Haiku 5.5 returned AccessDeniedException ("not available for this account") on the Free plan in the Bedrock playground, while Haiku 4.5 and Sonnet 4.6 worked. Retest Haiku 5.5 / Sonnet 5.5 later; switching back is a `.env` change. Exact Bedrock model IDs (possibly with a region prefix or version suffix) must be checked with a real call. Haiku 4.5 uses `budget_tokens` for thinking, so leave thinking off. (team)
41. **Bedrock via the legacy `AnthropicBedrock` client with IAM access keys and `us.` inference-profile model IDs. Not API keys, not the Mantle client.** Verified by real calls on 2026-11-13: Haiku 4.5 (530 ms) and Sonnet 4.6 (881 ms) work. Bedrock long-term API keys are blocked by an account-level policy (explicit deny on `bedrock:CallWithBearerToken`); the Mantle client returns 404 for these older models; bare model IDs fail ("on-demand throughput isn't supported"). Haiku 5.5 and Sonnet 5.5 return 403 "not available for this account" with both clients. Supersedes the client choice in #36. (Claude)
42. **A student can have one open quiz and one open proposal at once; replies are matched by vocabulary.** A/B/C goes to the quiz, YES/NO to the proposal. The vocabularies never overlap, so matching is unambiguous, and it lets the demo send the Socratic follow-up and the proposal back to back. Unclear replies ("maybe") get a clarifier and never an action. Short-answer quizzes would break this and need a different rule. (Claude)
43. **Engine structure enforces the approval gate by construction, not convention.** The Planner, Tutor and Scout get `Deps` with no calendar; only `approve.ts` calls `createEvent`, and Crew Lead merely hands it the writer. A test fails if any other engine file mentions a calendar. (Claude)
44. **Every LLM output goes through `safeText`: a timeout, a fallback, and an acceptance check.** The Socratic follow-up is rejected if it contains the correct answer; a proposal is rejected unless it states the day and weight and ends with "Reply YES or NO."; otherwise the code's own wording is sent. A slow or broken model can't leak an answer or stall the thread. (Claude)
45. **Per-student work is serialized with a promise queue.** Two quick texts can't overwrite each other's state. This is in-process only; a serverless/multi-instance deploy would need a real lock. (Claude)
46. **"In N days" counts calendar days in the student's timezone, not hours rounded up.** A real run showed the quiz saying "before Friday" while the proposal said "in 7 days" (an hours-based count at 10:55pm). The staged exam is now exactly 6 calendar days out at 10am. Tested at several times of day. (Claude)
47. **Proposal text is the code's template by default; model wording is opt-in (`llmProposals`).** In the first real run Haiku's version was stiff and repeated a wrong day count. The brief's example wording is the template, and the demo needs reliable text. The Socratic follow-up still comes from the model, with the answer-leak guard. (Claude)
48. **Photon route (`spaceId`, `senderId`) is part of the student record and survives demo switches and resets.** A real run caught "Switch to Week 6" wiping it (texts then failed with "no Photon route"). Regression test added. (Claude)
49. **Dashboard runs locally for the demo; the browser never sees the agent URL or the demo token.** Next route handlers proxy to the agent and strip the phone number, Photon route and quiz answers. Viewing is open; Approve and the `/demo` controls need the presenter key (`?key=<DEMO_ADMIN_TOKEN>`). The agent is on the laptop, so a Vercel deploy would need a tunnel; not worth it for the stage demo. Live updates by 1.5 s polling. (Claude)
50. **Google Calendar over plain HTTPS with only the `calendar.events` scope; refresh token in `.data/google.json` (gitignored, mode 600).** No SDK dependency. The sign-in start link requires the demo token and issues a one-time state nonce; the callback is rejected without it. Testing-mode refresh tokens expire after about 7 days, so connect again on demo week. (Claude)
51. **Calendar writes are idempotent: the approve path sends a key (proposal id + creation time), the adapter turns it into a deterministic Google event id.** A retry or a double YES can't double-book; a 409 counts as done. The creation time keeps a rerun after Reset from colliding with a deleted event. (Claude)
52. **Reset demo deletes the calendar events the demo created, and only those.** The adapter refuses any id that isn't our `sc…` hash, so reset can't touch real events. This is the one delete path; it exists so reruns don't stack events on the same slot. (Claude)
53. **If Google isn't connected, approved changes are kept locally and shown on the dashboard; the dashboard says "Calendar: local" vs "Google Calendar connected".** Matches the brief's fallback and avoids silently claiming a Google write. (Claude)
54. **The stage syllabus image is a fake one-page ECON 201 syllabus (`seed/macro-syllabus.jpg`, source `apps/web/public/macro-syllabus.html`) that matches the stored parse exactly.** Exam 2 at 25% covers Ch. 4-6, Week 9 is crowded, Week 1 start date given. Judges see the photo next to the result and it matches. (Claude)
55. **Judge QR flow: `/join` shows a QR for `sms:<line>&body=Hi%20Syllabus%20Crew`.** Open risk: a shared line only replies to numbers with an assignment, each using a seat of 25; untested with a second phone. (Claude)
56. **Syllabus reading is split: the model reads, code does the math.** The model returns the headline grading categories (as stated), and for each dated item which category it counts toward, plus dates/weeks and topics. Code computes each item's weight (category weight shared equally among its items), checks that categories add up to at most 100, resolves weeks to dates, finds crunch weeks, and decides what to ask. This replaced a first design where the model supplied per-item weights; on a real syllabus it double-counted sub-parts (110%) in every run. (Claude)
57. **Reader output is never trusted: strict validation, one retry that feeds the errors back, then a clean failure.** Checks include real calendar dates, known categories, and dates within a year of today (the real PDF never states the year, and the model guessed 2025 once). The prompt carries today's date. `temperature` cannot be used (the newer Claude models reject it), so consistency comes from validation. Real PDF: identical result in 3 of 3 runs, 1 attempt, about 14 s. (Claude)
58. **Crunch week = two or more deadlines in one Monday-Sunday week (small ones included); a lone big exam is not a crunch.** Matches the brief ("several exams and papers in the same week"). Only items 10%+ or of unknown weight get asked about, heaviest first. (Claude)
59. **The syllabus PDF is sent straight to Claude on Bedrock (Sonnet 4.6); Textract is not needed for PDFs.** The real syllabus lives in `seed/private/` (gitignored). (Claude)
60. **A failed text never leaves state behind: `ctx.say` sends first, then records.** The first design committed state before sending, so a Photon failure could leave a quiz nobody saw (spending a daily slot), mark Scout's material as found, or turn a successful calendar write into a false "couldn't add it". Now the approve path records the event before it texts, a proposal whose text failed is withdrawn, and tests cover each. Found by code review. (Claude)
61. **Quiet hours also gate Scout's text; a quiz that is already open is never overwritten; only one proposal is open at a time.** The demo "Send quiz now" control may replace an open quiz (the abandoned one counts as asked). "quiz me" with one open repeats it. (Claude)
62. **Strangers can't touch the presenter's calendar or bypass limits.** Anyone can scan the QR and text the line, so real Google writes are routed by owner (`calendarRouter`): only the demo student reaches Google, everyone else gets a local stand-in. Demo-mode bypass of quiet hours and caps is limited to the demo student. A sender may send 40 texts an hour; stored threads are capped at 200 messages. (Claude)
63. **The agent binds to 127.0.0.1, the dashboard to localhost; no CORS; presenter key is its own secret (`PRESENTER_KEY`), compared in constant time.** The browser only ever talks to the dashboard's own server. Sign-in result pages escape every value and never echo Google's error text. (Claude)
64. **After a restart the agent ignores Photon messages older than a minute before startup.** An old "YES" replayed by the socket must never act on whatever is pending now. (Claude)
65. **Before the repo goes public: rewrite history (or publish a fresh repo).** Early commits contain the presenter's real phone number, now removed from the files. A normal follow-up commit does not remove it from history. (Claude)
66. **Real syllabus upload is a presenter action on the dashboard (`/upload`), not an iMessage PDF.** Photon Beta iMessage takes text and images only. The upload goes through the dashboard's server (presenter key), to the agent, which refuses unless the student has already texted the line: the agent never starts a conversation. (Claude)
67. **A new syllabus is a new semester.** Installing one replaces the student's whole state (demo data, proposals, open quiz) and removes the calendar events the demo created; the Photon route and message thread are kept. Phase `live` marks real data; Reset demo goes back to Day 1. (Claude)
68. **Questions about a syllabus: one open at a time, heaviest first, answered in code.** Dates ("Oct 21", "10/21", "it's Dec 7th") and percents are parsed by deterministic code, with the year chosen closest to today and dates more than a year away rejected. One hint on an unclear answer, then the question is dropped for good; "skip" drops it at once. Normal commands ("quiz me", "what should I focus on") still work while a question is open. (Claude)
69. **Dashboard shows upcoming exam cards (max 3) and a timeline of every dated item, passed ones dimmed.** Small deadlines are in the timeline and in crunch-week detection but don't get cards. (Claude)
70. **Uploading the same file twice does nothing.** A real run sent the summary text twice (two uploads 69 s apart). The agent fingerprints the uploaded bytes; an identical upload for a student whose live syllabus already matches is acknowledged without re-reading or texting (saves a Bedrock call too). Reset demo clears it. (Claude)
71. **The reader's `topics` means "what the assessment covers or is based on", filled from the schedule between the previous assessment and this one.** The first category-based version returned no topics at all for the real PDF; the instruction was too vague. Now Essay #1 lists its readings, and the Tutor will have something to quiz on. (Claude)
72. **Quiz questions for a real syllabus are written by the model, but only the words: code builds and checks everything else.** The model returns a correct answer, two wrong ones, an explanation and a hint. Code validates length/format/distinctness, rejects hints that contain the answer or aren't questions, drops anything the model marked low-confidence, then shuffles the answers into A/B/C with a seeded shuffle (so the model can't bias the correct letter, and grading stays in code). (Claude)
73. **Every generated question is double-checked by an independent model call that never sees the key.** A second call answers the questions cold; only questions where it picks the same letter are kept. On the real syllabus: 0 disagreements of 6 kept, 3 of 9 rejected by format checks. Questions come from the model's knowledge of standard works (it is not given the reading's text), so obscure readings would yield fewer or weaker questions; grounding in the student's own slides/readings is a later step. (Claude)
74. **Question writing runs outside the per-student lock, one writer at a time.** It takes tens of seconds; the student's texts keep being answered meanwhile. Triggers: right after a syllabus is installed, the "Write quiz questions" demo control, or the first "quiz me" with none yet ("I'm writing your first questions now"). The student is told when they're ready, unless it's quiet hours. (Claude)
75. **Calendar titles use the short course name (text before the first colon).** "LIT 101: Antiquity: ..." was far too long for an event title. (Claude)
76. **The question writer retries a topic once with the exact rejection reasons, and the Bedrock client retries throttling (429) up to 6 times.** Real run: of 15 questions returned, 9 were rejected for answer length (a 60-character cap was too strict, now 90 with a request for under 70), and 2 of 4 topics died on "429 Too many requests" (a new AWS account has low limits; calls are also made two at a time, not three). After the fixes: 12 written, 12 kept, 0 rejected. Rejection reasons and errors are recorded in the writer's stats. (Claude)
77. **Long answer choices go on their own lines in the quiz text.** Choices of 40+ characters made one wrapped run-on line; now each gets its own line (short ones still share a line, as in the brief's example). (Claude)

78. **Asking for a quiz starts a round of 5 that continues by itself.** After each settled question (right, or revealed after two misses) the next one arrives after a short pause; a wrong first answer still gets the hint and waits for the retry. The round ends with a one-line summary (how many, how many first try, weakest topic). "stop" leaves it, "skip" passes on a question, and "next / more / again / keep going" start one. Found in real use: having to type "next question" after every answer was not automated. (Claude)
79. **A quiz the student asks for is a reply, so quiet hours and the 3-a-day cap don't apply to it; they still guard what the agent starts on its own.** Scout's and the demo control's quizzes stay single questions, gated as before. (Claude)
80. **Written questions get a cleaner layout; the hand-written demo questions keep the demo-script wording.** Header `Question 2 of 5 · The Book of Songs`, a blank line, the question, a blank line, one choice per line. Reading names are shortened (page ranges, "Selections from" and parentheticals dropped). (Claude)
81. **While a question is open, "I don't know" / "idk" / "no idea" / "I give up" count as a miss; "hint" is a free nudge.** Real use: "I do not know" got generic small talk. Now a first give-up gets the Socratic hint (and drops mastery like a wrong answer), a second reveals the answer and the round moves on; "hint" gives the hint with no penalty. If a proposal is also waiting, strong phrases go to the quiz and the softer "not sure" stays with the proposal. (Claude)
82. **Answers tolerate stray punctuation and short lead-ins** ("B\\", "b!", "I think B", "answer is c"); a mistyped 1-3 character reply while a question is open asks for A, B or C instead of becoming small talk. (Claude)
83. **"I don't know" right after a hint is giving up: the answer is revealed.** Real use: a free "hint" followed by "idk" got a second hint and no answer. Now a hint request marks the question as hinted, and a following give-up reveals the answer (as the second miss); without a prior hint, "idk" still gets the hint first. (Claude)
84. **A one-line tip under the first question of each round (and one-off quizzes): `Stuck? Just text "hint" and I'll give you a nudge.`** Not repeated on questions 2-5, to avoid nagging. (Claude)
85. **The Nudger's decisions are code; wording is templated.** Whether to nudge, which kind, and why not live in `packages/core/src/nudger.ts` and are covered by tests. Kinds: `mastery` (weak topic on an assessment inside its window, "want a quick round?"), `quiz` (known topic, 2+ days out), `deadline` (plain heads-up, within a day or when nothing can be quizzed). Lead time scales with stakes (30%+ a week, 10% four days, 5% two days, smaller only the day before). The model could write wording, but the earlier proposal experiment showed templates read better and keep the demo predictable. (Claude)
86. **Hard rules for proactive texts: 11pm-8am never; nudges only 9am-8pm; 3 a day with Scout counted; a 4-hour gap; not within 30 minutes of the student's last text; not while a question, proposal, syllabus question or offer is open; one nudge per item per day; back off after two unanswered nudges (unanswered = no reply within 12 hours), except a 20%+ deadline tomorrow.** Quiz offers expire after 6 hours; a late YES does nothing. (Claude)
87. **Reminders the student asks for are always delivered.** Parsed by code ("remind me Sunday to start the essay", "in 2 hours", "tomorrow at 5pm", "on Dec 3"; default 9am). They ignore mute and the daily limit; only quiet hours delay them (to 8am, with a "sorry, this is late" lead-in). (Claude)
88. **A quiz the agent offers is a yes/no question like a proposal.** YES starts a 3-question round on the weak topic; NO drops it. If a proposal is also waiting, YES/NO belong to the proposal. (Claude)
89. **The scheduler defaults to dry-run (`SCHEDULER=dry`): it logs what it would send and sends nothing.** `on` really texts. Two demo controls: "what would you do now? (dry run)" applies the real rules and shows the decision; "Run Nudger now" skips the timing rules (and the morning quiz) to show a nudge live, but still never interrupts an open question and never texts someone who hasn't texted the line. (Claude)
90. **Scout's texts count toward the 3-a-day limit and obey quiet hours; "pause", "stop nudging me" and "resume" control nudges.** (Claude)
91. **"skip" means "skip this question" whenever a question is open; it only declines a proposal when none is.** Real use: with a question and a proposal both waiting, "skip" declined the proposal and left the question (and the round) stuck, which also blocked the Nudger. "no" still always answers the proposal. (Claude)
92. **A quiz offer on a weak topic beats a plain reminder, unless a 10%+ deadline is within a day; a forced (demo) run also ignores the lead-time window.** Real data showed the real rules correctly stay quiet when the next deadline is 16 days away, so the demo control would have shown nothing. A forced run now picks the best upcoming nudge however far away. Without force, the lead-time windows still apply. (Claude)
93. **The student names the agent and picks a vibe; "Syllabus Crew" stays the product name.** First contact: who it is, "what do you want to call me?", then CHILL / STRICT / HYPE, then one open question (which class worries you most). All parsed in code (`packages/core/src/naming.ts`); a command, a question, a bare YES / A / B / C or a photo is never taken as a name and is handled normally. Rename ("call yourself Kiki") and vibe change ("be strict") work at any time. The vibe only changes set phrases (correct / miss / nudge wording); chill is the original wording, so the stage demo text is unchanged. Reset demo clears the name; Week 6 and a new syllabus keep it. (User + Claude)
94. **The agent may text first, but only on request and only into a known thread.** The user asked for the first message in the chat to come from the agent, as Poke and Boardy do (number captured on a website, then the agent reaches out). `startOnboarding` is behind the presenter's "Say hello" control and refuses when Photon has no thread for the number. This replaces "never texts first" in CLAUDE.md; the scheduler still skips anyone who has not opted in. A public sign-up form is not built: it would need per-number shared-line assignment and abuse protection. (User + Claude)
95. **Dashboard restyled ("Study Desk"); sender labels come from the message `kind`.** Ruled cream paper, Fraunces + Figtree, stationery characters (speech bubble, binoculars, flashcard, calendar page, bell) so it does not read as a copy of the Elfie reference. The crew tree is pinned and revealed by scroll on wide screens, static on narrow screens and with reduced motion. No agent change was needed for the labels: scout -> Scout, quiz/tutor -> Tutor, proposal/approval -> Planner, nudge/reminder -> Nudger, everything else -> the agent's name. (User + Claude)
96. **No presenter key on the dashboard.** The user found the `?key=` step annoying for a hackathon. The dashboard binds to 127.0.0.1, so only the laptop can reach it; the control routes now check only that the request is same-origin from localhost, which stops another website in the same browser from pressing the buttons. The agent still requires its own token, which the browser never sees. Deploying or tunnelling the dashboard would need a real lock again. (User)
97. **A syllabus texted as photos or a PDF is read for real, behind a "staged photo" switch that defaults to staged.** With the switch off, each texted file is downloaded from Photon when needed, identified by its first bytes (iMessage does not say), and HEIC or oversized photos are converted to a 2000px JPEG with macOS `sips` because the model cannot read HEIC. Pages arrive as separate texts, so the agent acknowledges the first and reads after 6 quiet seconds, up to 12 pages, in arrival order. The read and install reuse the upload path (same reader, validation, duplicate hash, question writer). The switch stays on by default so the rehearsed stage demo is instant and cannot stall on a model call; `/demo` flips it while running, `STAGED_PHOTO=false` changes the default. (User + Claude)
98. **PDF is the way in; a texted PDF is always read for real, with no switch.** The user tried texting screenshots and found them rough: nobody will send a syllabus page by page. Now a texted PDF is read for real whatever the staged-photo setting is (the file is downloaded first to see what it is, with a 3 second limit; a slow or failed download counts as a photo). Photos keep the staged Macro shortcut for the stage demo, extra photos sent together get no reply each, and the agent's wording asks for a PDF. The two switch buttons were removed from /demo; `STAGED_PHOTO=false` still makes photos read for real. (User)
99. **Student state can live in Amazon DynamoDB (`STORE=dynamo`); the local file stays the default.** One on-demand table, `<DYNAMODB_TABLE_PREFIX or syllabus-crew>-students`, one item per student keyed by phone number, with readable columns (phase, agentName, course, updatedAt, messageCount) and the full state as JSON (gzipped above 300 KB, under DynamoDB's 400 KB limit). Reads come from memory loaded at start, because the dashboard polls every 1.5 s; saves write through in the background, the newest state per student wins, and a failed write is retried and logged instead of breaking a reply. The agent refuses to start if the table can't be read, so a bad setup shows at start, not mid-demo. One agent process is assumed (no cross-process locking). `npm run dynamo:setup` creates the table and copies `.data/state.json` in. (User + Claude)
100. **The stage demo starts with the real PDF, not the saved photo.** The user wants the only setup step to be attaching the syllabus PDF, and the script's line "it read the syllabus" must be literally true. A PDF is read at once (no wait for more pages), about 7-10 s on the stage syllabus. Question batches that finish after the semester changed (Week 6, Reset, another syllabus) are dropped silently, so no "I wrote 9 questions" text lands mid-demo. The photo keeps the instant saved copy as the fallback if the AI service is slow. (User)
101. **Free chat sees the recent thread, and asking for study time goes to the Planner in code.** On the real phone, "No, I think it's B" got "which question?"
